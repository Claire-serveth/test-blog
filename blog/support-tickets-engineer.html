How many support tickets need an engineer?

Most pings to your engineering team did not need one. Here is how we investigate a ticket first, and what a finished escalation looks like when it really is a bug.

CNY

Cindy

Technical Support, Serv.eth

Open a protocol’s Discord during launch week and you will see the same scene play out again and again. A user posts a screenshot and a one-line complaint. Someone tags a core contributor. Twenty minutes later an engineer is reading a transaction hash instead of shipping.

This costs more than it looks like it does. Each ping takes the time to answer the ticket, plus the time it takes to get back into whatever the engineer was doing before. Most of those pings did not need an engineer at all.

What your support tickets are really about

Most support queues sort into the same few categories. The percentages vary by protocol, but in nearly every queue, user setup and understanding issues far outnumber real bugs.

Two of those buckets get mistaken for bugs more than any other: pending transactions and confusing interfaces. They look like bugs because the user cannot see what is happening. A support team’s job is to make it visible.

How we investigate a ticket before escalating it

Many tickets look like bugs on first read. A user says their funds are gone, or a transaction has been stuck for hours, and the obvious move is to ask an engineer. A good support team checks the facts first. This is the order we work in:

  1. Ask for two things only, the transaction hash and the wallet address. Long questionnaires make users give up.
  2. Open the hash in the block explorer and read the status. A failed transaction shows a revert reason. A pending one points to a gas or nonce problem.
  3. Read the event logs to see what the contract actually did, such as which tokens moved and in what amount.
  4. Check the protocol’s public API for the backend state of the position or order, and compare it with what the chain shows.
  5. Compare all of that with what the user sees. Display issues, missing token imports and the wrong network explain a large share of reports.
  6. Decide. Either explain the cause and close the ticket, or escalate with the evidence attached.
Most tickets end at step 6 with an explanation, and no developer is pinged. The user also learns what happened, which stops the same ticket from coming back next week.

When it is a bug, hand over a finished file

Some tickets are real, and the handoff is where a support team earns its place. An engineer should be able to read the message once and start working. This is the shape we use:

Summary      [one line describing the problem]
Network      [chain name]
Transaction  [transaction hash]
Wallet       [wallet address]
Expected     [what should have happened]
Observed     [what happened instead]
Ruled out    [what we already checked]
Reproduced   [steps taken and how often it happens]
Affected     [number of users reporting it]
Links        Explorer, screenshots, ticket thread

The Ruled out line does the most work. It tells the engineer which theories are already dead, so they start where the investigation ended instead of where it began.

What this means for your team

A support team that sends fewer false alarms to engineering saves hours. It also tends to catch real problems sooner, because the person answering tickets has seen three similar reports and connects them before anyone files a formal bug.

The way we work is simple. We take the front line. We investigate before we escalate. When something does reach your developers, it comes with evidence attached.
